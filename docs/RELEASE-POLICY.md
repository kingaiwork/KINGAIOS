# KINGAI OS Release Policy

KINGAI OS uses four public engineering channels:

```text
dev -> beta -> rc -> stable
```

The policy applies to four official distribution forms:

```text
Server
Desktop (personal computer / PC)
IoT / Edge
Container (Docker / OCI)
```

A capability is never promoted only because source code exists or a version number changes.

## Shared release truth

KINGAI OS distinguishes:

1. source exists;
2. CI passes;
3. runtime/VM/hardware path is verified;
4. artifact is published;
5. production readiness is approved.

`release/gates.json` is fail-closed and represents machine-readable release evidence.

## Dev

Dev may expose incomplete functionality.

Allowed characteristics:

- Developer Preview artifacts;
- incomplete UI/runtime features;
- non-production signing;
- non-installable preview images when clearly labeled;
- experimental adapters;
- developer container tags;
- known limitations documented publicly.

Dev must still avoid false production claims and must not distribute secrets/private signing keys.

## Beta

Shared requirements:

- repeatable build workflow;
- core CI;
- unit tests and static analysis;
- artifact-specific smoke test;
- dependency/package inventory;
- license inventory;
- SBOM generation path;
- documented known limitations;
- rollback/recovery strategy appropriate to the artifact type;
- security review of new privileged surfaces.

### Server/Desktop Beta

Additionally requires:

- boot validation;
- installer validation where installation is enabled;
- update state validation;
- recovery path;
- hardware/VM compatibility evidence.

### IoT/Edge Beta

Additionally requires:

- architecture image validation;
- concrete Device Pack for any hardware listed as supported;
- OTA/update strategy;
- recovery behavior;
- device capability policy.

### Container Beta

Additionally requires:

- amd64 and arm64 Buildx verification for architectures advertised;
- non-root default runtime unless explicitly justified;
- no unrestricted host Docker socket/root filesystem dependency by default;
- persistent-state migration policy;
- health/readiness behavior;
- OCI SBOM/provenance generation;
- vulnerability scanning workflow.

## RC

Shared RC requirements:

- production-grade signed update/artifact metadata where applicable;
- no open release-blocking security defects;
- release evidence freshness checks;
- final artifact manifest/checksum;
- SBOM and provenance;
- release notes;
- legal/license review for shipped components;
- protected release authority.

### Bootable OS RC

Server/Desktop and supported bootable Edge targets additionally require:

- clean install validation;
- upgrade validation;
- A/B or equivalent atomic rollback validation when part of the product update model;
- recovery validation;
- Secure Boot release chain when Secure Boot is claimed;
- production TUF/update trust chain when secure update is claimed;
- supported hardware/VM matrix.

### Container RC

Container additionally requires:

- multi-architecture manifest validation;
- signed OCI image/attestation policy;
- registry publication verification;
- vulnerability threshold policy;
- persistent-state compatibility tests;
- rollback by known-good immutable image reference;
- no production-like tag generated by a developer-only publishing workflow.

## Stable

Stable requires all applicable RC gates plus:

- reproducible-oriented release provenance;
- final SBOM;
- signatures/checksums/attestations appropriate to artifact type;
- support lifecycle commitment;
- security advisory process;
- release notes and migration notes;
- legal/compliance review;
- protected branch/release governance;
- tested distribution path;
- documented upgrade and rollback policy.

A Stable release is never created merely because a version number is changed.

## Artifact-specific update semantics

Bootable OS editions:

```text
signed metadata
 -> staged update
 -> inactive slot or equivalent
 -> verify
 -> boot
 -> health gate
 -> commit / rollback
```

Container edition:

```text
signed/verified OCI reference
 -> deploy new immutable image
 -> health/readiness gate
 -> retain persistent KINGAI state separately
 -> promote / roll back image reference
```

The Container edition does not pretend disk-slot A/B semantics exist inside an OCI image.

## Protected production gates

The following must remain false until separately verified:

- production TUF repository/key operations;
- production signing readiness;
- protected release governance;
- production object-storage delivery;
- production container signing/registry policy;
- hardware-specific Device Packs that have not been boot-tested.

# 中文发布策略

KINGAI OS 使用：

```text
dev -> beta -> rc -> stable
```

并覆盖四个正式版本：

- Server；
- Desktop（个人电脑 / PC）；
- IoT / Edge；
- Container（Docker / OCI）。

## 共用原则

必须区分：

```text
代码存在
CI 通过
VM/运行时/硬件验证
Artifact 已发布
Production Ready
```

这五个状态不能混为一谈。

## Server / Desktop

进入 RC/Stable 前需要安装、启动、更新、回滚、Recovery、Secure Boot/TUF（如果宣称支持）、硬件/VM 兼容、SBOM、签名与 Release Governance 等系统级门禁。

## IoT / Edge

除了通用架构镜像，还必须通过具体 Device Pack 的真实硬件验证，才能把 Raspberry Pi、Jetson 或工业设备写成正式支持。

## Container

Container 不使用磁盘 A/B 的假概念，而采用不可变 OCI 镜像替换与持久化状态分离。

进入 Beta/RC 需要：

- 宣称架构对应的 amd64/arm64 Buildx 验证；
- 非 root 默认运行；
- 不默认把 Docker Socket/宿主机根目录交给 Agent；
- SBOM/Provenance；
- 漏洞扫描；
- OCI 签名/Attestation 策略；
- 持久化状态兼容性；
- 健康检查与镜像回滚策略。

Stable 永远不能因为“改了版本号”自动产生。
